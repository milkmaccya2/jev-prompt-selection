# ラベル付けの基準

実際のエージェントは、発話ごとに**プロンプトを1つ決める**前提です。
候補は12個です。

- 専用プロンプト11個: 常に載せる3部品(人格・安全・出力形式)+ その分野の部品1つ
- `base`(基本プロンプト): 常に載せる3部品だけ

`data/eval.jsonl` の各件には次の2つを付けます。

- `answer`: 選ぶべきプロンプト1つ
- `acceptable`: それを選んでも可とするプロンプト(複数の分野にまたがる発話のみ)

## 基本ルール

1. **`answer` は、ユーザーの目的に対応するプロンプトにする。**
   「名駅あたりで事務の正社員」は、目的が求人探しなので `search_conditions`。地名の言い換えは補助なので `acceptable`。
2. **複数の分野にまたがる発話は、主な1つを `answer` にし、残りを `acceptable` にする。**
   例: 「面接で希望年収聞かれたら?」は `interview_prep`(可: `salary_benefits`)。
3. **専用の指示がいらない発話は `base`。** 常に載せる部品とツールだけで答えられるもの。
   - ツール操作だけで済む: 「応募したい」「キープして」「面接何回?」「ほかにもある?」
   - 相づち・保留: 「はい」「ちょっと考えます」
   - 安全の部品が担当する: 心身の不調の訴え、闇バイトの疑いの相談
4. **あいさつ・お礼・雑談・求人と無関係な質問・不適切な依頼は `out_of_scope`**(範囲外の話題の部品が扱うため)。
5. **ツールは判定の対象外。** 常に渡す前提とする。
6. 迷った件には `ambiguous` タグを付け、`note` に判断理由を書く。

## プロンプトごとの判断基準

| プロンプト | `answer` にする条件 |
|---|---|
| `search_conditions` | 求人を探す・条件を変える/聞き出す |
| `query_normalization` | 地名・職種の言い換えそのものが目的(今回のデータには該当なし。検索の `acceptable` としてのみ登場) |
| `company_info` | 特定企業の事業・規模・安定性・公開データ |
| `reviews` | 評判・クチコミ・実態・投稿の相談 |
| `salary_benefits` | 給与・手取り・残業代・休日・福利厚生・交渉 |
| `career_advice` | 転職の迷い・適性・方向性・強み・ブランク・年齢の不安 |
| `application_docs` | 履歴書・職務経歴書・志望動機・応募メッセージ・Web履歴書 |
| `interview_prep` | 面接の準備・想定質問・答え方・模擬面接 |
| `account_terms` | ログイン・登録・通知・退会・規約・料金・個人情報 |
| `error_handling` | ユーザーが不具合を報告、または直前のツールが失敗 |
| `out_of_scope` | あいさつ・お礼・雑談・求人と無関係な話題・不適切な依頼 |
| `base` | 上記の専用の指示がいらない |

## タグ

`single`(1分野で素直)/ `cross`(複数分野)/ `ambiguous` / `out_of_scope` / `colloquial`(口語・略称)/
`typo` / `context`(直前の会話が必要)/ `base`(answer が base)

## 既知の限界

- ラベルは作成者1名による付与で、二重チェックはしていない。
- 発話は合成データで、作成者が部品の内容を知ったうえで書いているため、実際の発話より部品の言葉に寄っている可能性がある。
- `query_normalization` は単独で `answer` になる件がない。プロンプトを1つ選ぶ設計では、検索プロンプトに統合するのが自然。
