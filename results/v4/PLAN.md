# v4 の測定計画: 4構成の同時比較

作成: 2026-10-09(測定の前に保存)。この計画は実行の前に確定し、結果を見たあとで指標・比較・採点のしかたを変えません。変えた場合は、変えた点と理由を summary に書き、計画どおりの数字も残します。

## 問い

**判断を返す API は、プロンプトの振り分けに使えるか。** Jev・OpenAI Decisions API・通常の LLM 分類器を、同じ実行の中で同じ条件で比べます。

## 位置づけ

- v3 本編(2026-10-04)と、Decisions API の追加測定(2026-10-08)の結果は、履歴としてそのまま残します。v4 の結果は `results/v4/` に置きます。
- 古い実行結果に Decisions API の結果だけを足した比較ではありません。4構成すべてを、1回の実行の中で測り直します。
- **test 100件は、v3 で凍結し、すでに結果を見たことのあるデータの再利用です。** 新しい、独立した、未知のデータでの評価としては扱いません。
- dev の本評価はしません。v4 のレポートに dev の数字は入れません。

## データと正解

| 項目 | 内容 | 確認方法 |
|---|---|---|
| 評価データ | `data/eval.v3.test.jsonl`(100件、正解・別解つき) | sha256 `437f6508…`(`results/v3/FROZEN.md`) |
| 指示文・候補の説明文 | `data/candidates.v3.json` から組み立てた文字列 | `descriptionsHash()` = `3e178125…` |
| 正解の基準 | `data/LABELING.v3.md` | sha256 `1bfc13c2…` |

実行スクリプトは、最初の呼び出しの前と最後の呼び出しの後に、`results/v3/FROZEN.md` の8項目(上の3つを含む)のハッシュを確かめます。一致しなければ呼ぶ前に止まり、実行後に変わっていれば集計しません。

## 比べる構成(4構成 × 2粒度 = 8)

| key | 構成 | 呼び方 | 主な設定 |
|---|---|---|---|
| `jev` | Jev | TypeSafe `POST /v1/systemone`(SDK `@typesafe-ai/sdk`) | `jev-latest`、choice の質問1つ |
| `dec` | gpt-6-luna(Decisions API) | OpenAI `POST /v1/decisions`(SDK `openai`) | choice の質問1つ |
| `luna` | gpt-6-luna(Chat) | OpenAI Chat Completions | `reasoning_effort: none`、構造化出力(候補 id の enum、strict) |
| `nano` | gpt-5.4-nano(Chat) | OpenAI Chat Completions | `reasoning_effort: none`、構造化出力(候補 id の enum、strict) |

- 通常 API(`luna`・`nano`)の設定は、v3 の実装(`src/v3/classifiers.ts`)のままです。
- モデルは上の4つに固定します。使えなくなっていた場合は、別のモデルに置き換えずに止めて相談します。
- 粒度: **12候補が主な結果、6分類は補足**です。6分類は v3 と同じ対応(`results/v3/PLAN.md` 2章)で、この検証で作ったまとめ方です。本番の分類とは別物です。

### 入力をそろえる方法

どの構成にも、同じ指示文、同じ候補の説明文、同じ会話(`recent_turns` と `user_utterance` の JSON)を渡します。API ごとに必要な形式の変換だけをします。

| 構成 | 指示文 | 候補 | 会話 |
|---|---|---|---|
| Jev | choice の `instructions` | `criteria`(id → 説明文) | `state` |
| Decisions API | choice の `instructions` | `choices`(`value` = id、`description` = 説明文) | `input` に JSON の文字列 |
| Chat(luna・nano) | system の先頭 | system の候補一覧(`- id: 説明文`)と出力の enum | user に JSON の文字列 |

## 測り方

- 1台の端末から1件ずつ順番に呼びます。並列にはしません。
- 各件で8つの呼び出しの順番を、種 `20261009` の乱数で並べ替えます。各件の順番を生データに残します。
- 自動リトライは0回です(TypeSafe SDK `retry.maxRetries: 0`、OpenAI SDK `maxRetries: 0`)。1回の呼び出しは30秒でタイムアウトします。
- **失敗(API エラー、タイムアウト、候補 id として読めない応答、拒否)は記録し、不正解として採点します。**
- ウォームアップには、評価対象外の既存の例を使います。基準書の例(`data/labeling-examples.v3.json`)の0・1・19番の3発話を全構成で1回ずつ呼び、採点しません。dev・test の発話と一致しないことを、スクリプトが呼ぶ前に確かめます。
- 記録するもの: 呼び出しの時刻、API が返したモデル名、SDK のバージョン(`openai`・`@typesafe-ai/sdk`)、主な設定、トークン数(入力・出力・キャッシュの読み出し・書き込み・推論)、判定時間、費用、選んだ候補、確信度、候補ごとの確率、エラー。
- **予算で止まった実行、途中で終わった実行、ハッシュが変わった実行は、完了した評価として集計しません。**

## 手順と費用の上限

上限は、動作確認と本評価を合わせて **$1** です。

| 手順 | コマンド | 見込み(最大) | 上限 |
|---|---|---:|---:|
| 見積もり | `npx tsx src/v4/eval.ts --set test --dry-run` | $0 | - |
| 動作確認 | `npx tsx --env-file=.env src/v4/eval.ts --set dev --limit 5 --smoke --budget-usd 0.05` | 約 $0.012 | $0.05 |
| 本評価 | `npx tsx --env-file=.env src/v4/eval.ts --set test --budget-usd 0.40` | 約 $0.154 | $0.40 |
| 集計 | `npx tsx src/v4/report.ts` | $0 | - |

- 動作確認には dev の最初の5件を使います。test の発話を本評価の直前に送ると、OpenAI 側でその発話までキャッシュが効き、その件だけ有利になりうるためです。動作確認の結果は集計に使いません。
- 見込みは、キャッシュが一度も効かない場合の o200k による概算です。Jev の入力トークンは実際には概算より多い(v3 で約2,050)ですが、単価が低いので、上限への影響は小さいです。
- 動作確認で問題がなければ、そのまま本評価に進みます。上限を超える見込み、入力条件の変更が必要、既存データの不整合のどれかがあれば止めて相談します。

## 指標

### 正確さ

| 指標 | 内容 |
|---|---|
| **主指標** | **12候補で、正解(`answer`)と一致した割合**。95% 信頼区間(Wilson) |
| 補足 | 別解(`acceptable`)を含む一致率と 95% 信頼区間 |
| 失敗 | 構成ごとの失敗した呼び出しの件数(不正解として数える) |

### 検定(事前に決める比較群)

| 比較群 | 中身 | 補正 |
|---|---|---|
| **主な比較群** | **12候補・答えと一致**で、4構成の総当たり6組(Jev 対 Decisions、Jev 対 luna Chat、Jev 対 nano Chat、Decisions 対 luna Chat、Decisions 対 nano Chat、luna Chat 対 nano Chat) | Holm(6組の中で) |
| 補足の比較群 | **6分類・答えと一致**で、同じ総当たり6組 | Holm(6組の中で、主な比較群とは別) |

- 検定は、対応のある McNemar の正確検定(両側)です。
- 「差がある」と書くのは、Holm 補正後の p が 0.05 未満の組だけです。
- 補正後の p が 0.05 以上の組は「この100件では差があるとは言えない」と書きます。「同等の精度」とは書きません。
- 別解込みの一致率と、補足の比較群の結果を、主な結果には昇格させません。

### 速さ

- 構成ごとの判定時間の p50 と p95 です。成功した呼び出しだけで計算し、失敗の件数は別に書きます。
- 倍率を示すときは「p50 どうしの比」のように、何の比かを書きます。
- 1台の端末からの1回の実行での観測として書きます。一般的な速さや SLA としては書きません。

### 費用

- 実際の usage と公式の単価から計算した、1000回あたりの費用です(実績)。
- 入力・出力トークン数、通常 API のキャッシュの読み出し・書き込みの内訳を出します。
- **試算は実績と分けて書きます。** 通常 API の「キャッシュが効かない場合」の試算は、次の条件で計算します。
  - gpt-6-luna: キャッシュの読み出し・書き込みとして返ってきたトークンも、すべて書き込み単価(入力の1.25倍)で払う
  - gpt-5.4-nano: 書き込み単価がないので、入力単価で払う(実績もキャッシュに乗らない見込み)
- Decisions API は専用の料金体系(入力だけ課金、出力・キャッシュは課金なし)で計算し、通常 API のキャッシュ割引は使いません。
- 単価と確認日・出典は `results/v4/PRICING.md` に書きます。

### 確信度と誤り

- Jev と Decisions API の `confidence` で、区間(0.5未満 / 0.5〜0.7 / 0.7〜0.9 / 0.9以上)ごとに件数と答えとの一致率を出します。12候補が主、6分類は補足です。
- 選んだ候補の確率(`probabilities` のうち選んだ候補の値)は、`confidence` と混ぜず、別の表として参考に出します。
- 確信度0.9以上で誤りがなかった場合も、「この test 100件の、この粒度では」と範囲を限定して書きます。
- 誤分類の例を、test の実際の結果から数件示します(id・発話・正解・別解・各構成の選択・確信度)。実測していない例は作りません。
- 「確信度が低いときに LLM に回せば改善する」とは書きません(今回は検証していません)。
