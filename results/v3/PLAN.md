# v3 の測定計画

この計画は、測定を始める前に書いて承認を受けるものです。承認後は変えません。結果を見たあとで指標・比較・採点のしかたを変えた場合は、変えた点と理由を summary に書き、計画どおりの数字も残します。

## 1. 何を比べるか

発話ごとにシステムプロンプトを1つ選ぶ分類を、次の構成で比べます。

| 構成 | モデル | 設定 | 12候補 | 6分類 |
|---|---|---|:-:|:-:|
| Jev | `jev-latest`(`jev-1.13.0`) | choice | ○ | ○ |
| gpt-5.4-nano | `gpt-5.4-nano` | 推論なし(`reasoning_effort: none`) | ○ | ○ |
| gpt-6-luna | `gpt-6-luna` | 推論なし | ○ | ○ |
| gpt-6-sol | `gpt-6-sol` | 推論なし | ○ | ○ |
| gpt-6-luna 推論 low(参考) | `gpt-6-luna` | `reasoning_effort: low` | ○ | - |

合わせて9構成です。

- どの構成にも、同じ指示文・同じ候補の説明文・同じ直前の会話と発話を渡します。指示文と説明文は `data/candidates.v3.json` から作ったもので、step 1 で凍結しました。
- Jev には `state`(会話)と choice の質問として渡します。LLM には、system に指示文と候補一覧、user に会話の JSON を渡し、候補 id の enum で構造化出力させます(Chat Completions)。
- 呼び出しのコード: `src/v3/classifiers.ts`、実行: `src/v3/eval.ts`。

## 2. 6分類の中身

| 6分類 | 含める12候補 |
|---|---|
| 相談(`consult`) | `career_advice`, `search_conditions`, `query_normalization` |
| 書類作成(`docs`) | `application_docs` |
| 情報提供(`info`) | `company_info`, `reviews`, `salary_benefits` |
| ハウツー(`howto`) | `interview_prep`, `account_terms`, `error_handling` |
| 範囲外(`out_of_scope`) | `out_of_scope` |
| 基本(`base`) | `base` |

- **この6分類は、候補を粗くまとめたときに正解率がどう変わるかを見るために、この検証で作ったまとめ方です。本番の分類とは別物です。** 6分類の結果から、本番の分類での正解率は言えません。
- 6分類の構成は、6つの分類の説明文から1つを選びます。12候補の結果を6分類にまとめ直したものではありません。
- 6分類の正解は、12候補の正解を上の表で写したものです。別解も同じように写します(写した結果が正解と同じ分類になる別解は、6分類では意味がなくなります)。

## 4. 指標

### 主な指標

**test での「答えと一致した割合」**です。正解(`answer`)と同じ候補を選んだ件数 ÷ 100。別解(`acceptable`)は含めません。95% 信頼区間(Wilson)を付けます。

### 主な比較

**Jev と各 LLM の比較を、McNemar の正確検定(両側)で行います。12候補と6分類それぞれで行います。**

- 比べる組: Jev 対 gpt-5.4-nano、Jev 対 gpt-6-luna、Jev 対 gpt-6-sol。12候補と6分類で、合わせて6組です。粒度は混ぜません(12候補の Jev と12候補の LLM を比べる)。
- 同じ100件での勝ち負けを数えます。b = Jev だけが正解した件数、c = 相手だけが正解した件数。p 値は b と c だけから計算します。
- 6組を同時に検定するので、**Holm 法で補正した p 値も並べます。「差がある」と書くのは、補正後の p が 0.05 未満の組だけ**にします。補正前の p も表に残します。
- 補正後の p が 0.05 以上の組は「この100件では差があるとは言えない」と書きます。「差がない」「同等」とは書きません。100件では、数ポイントの差は検出できないためです。b と c の件数も必ず並べます。
- gpt-6-luna 推論 low(参考)と Jev の比較も表には載せますが、主な比較の6組には入れず、Holm 法の補正にも含めません。

### 副指標

| 副指標 | 中身 |
|---|---|
| 別解込みの正解率 | 正解か別解のどれかを選んだ割合(95% 信頼区間つき)。Jev と各 LLM の McNemar 検定も参考として出す |
| 判定時間 p50 / p95 | 1回の呼び出しにかかった時間(手元の端末で測った、送信から応答まで)。成功した呼び出しだけで計算し、失敗の件数は別に書く |
| 1000回あたりの費用 | 実際のトークン数 × 公式の単価(`results/v3/PRICING.md`)。OpenAI は「今回の実績」と「毎回キャッシュが切れた場合」の2つを出す。Jev と同じ費用になるキャッシュのヒット率も出す |
| 確信度の区間ごとの正解率 | Jev だけ(LLM は確信度を返さない)。区間は 0.5未満 / 0.5〜0.7 / 0.7〜0.9 / 0.9以上。区間ごとに件数・平均確信度・正解率・別解込みの正解率を出す。12候補と6分類それぞれ |

ほかに、次のものも出します。

- 取り違え(別解でも救えなかったもの)の一覧。正解 → 選んだ候補
- 6分類の対応表(行 = 正解、列 = 選択)
- 失敗した呼び出しの件数と中身(構成ごと)
- 呼び出しの順番ごとの判定時間 p50(順番を入れ替えたことで偏りがないかを見るため)

## 5. 採点のしかた

- **失敗した呼び出しは不正解として数えます。** 失敗は、API のエラー、30秒のタイムアウト、構造化出力が候補 id として読めない応答、拒否のどれかです。v2 では失敗を「基本プロンプトを選んだ」として採点していましたが、v3 では正解が `base` の件でたまたま正解になることを避けるため、不正解にします。
- 失敗した件数は構成ごとに書きます。失敗を除いた正解率も参考として並べます。
- 1つの構成で失敗が10件以上出た場合は、API の障害の可能性があるので、summary を書く前に止めて報告します。失敗した件だけを呼び直すことはしません。

## 6. 測り方(v2 から変えた点)

| | v2 | v3 |
|---|---|---|
| 呼ぶ順番 | 各件で、いつも Jev 12候補が最初 | **各件で9構成の順番をランダムに並べ替える**。乱数の種は `20261004` に固定し、各件の順番を生データに残す |
| 自動リトライ | SDK の既定(最大2回) | **0回**。TypeSafe SDK は `retry: { maxRetries: 0 }`、OpenAI SDK は `maxRetries: 0`。失敗は失敗として記録する |
| タイムアウト | Jev 30秒、OpenAI は SDK の既定 | **どちらも1回30秒** |
| 説明文・指示文 | プロンプト部品の frontmatter から作った | `data/candidates.v3.json`(凍結済み)から作る |
| 正解 | 基準書 v2 によるラベル | 基準書 v3 によるラベル(dev は付け直し、test は新規) |

変えていない点:

- 1台の端末(macOS、arm64)から、1回ずつ順番に呼びます。並列には呼びません。
- 各セットの最初の3件を、全構成で一度ずつ呼んでから捨てます(ウォームアップ)。そのあと100件すべてを採点に使います。最初の3件は2回呼ぶことになりますが、採点するのは2回目です。
- LLM の system は全件で同じなので、OpenAI 側の自動プロンプトキャッシュが効きます。効いた割合を出します。v2 と同じく、gpt-5.4-nano のプロンプト(約1,400トークン)はキャッシュに乗らない見込みです。

## 7. 実行の手順

1. `npm run v3:frozen` で、凍結した入力のハッシュが `FROZEN.md` と一致することを確かめる。実行スクリプトも、最初の呼び出しの前と最後の呼び出しの後に同じ確認をして、結果を生データに残す。一致しなければ呼ぶ前に止まる
2. **5件で動作確認**: `npm run v3:eval -- --set dev --limit 5 --warmup 0 --smoke --budget-usd 0.10`
   - dev の最初の5件を使う(test の結果を本番の前に見ないため)
   - 確認すること: 9構成すべてが応答する、失敗が0件、費用が見込みと合う、生データにキーや認証情報が入っていない
   - 結果は `results/v3/raw/smoke-*.json` に出し、集計には使わない。問題があれば、本番の前に止めて報告する
3. **本番**: test を先に、dev をあとに、それぞれ1回ずつ実行する
   - `npm run v3:eval -- --set test --budget-usd 1.50`
   - `npm run v3:eval -- --set dev --budget-usd 1.50`
4. 集計と summary の作成(`src/v3/report.ts`、step 6 で書く)

### 費用の見込みと上限

`npm run v3:eval -- --dry-run` で計算した、キャッシュが一度も効かず全部書き込み単価になる場合の見込みです。

| | 呼び出し回数 | 見込み(最大) | 上限(`--budget-usd`) |
|---|---:|---:|---:|
| 動作確認(5件) | 45 | 約 $0.05 | $0.10 |
| test(ウォームアップ3件 + 100件) | 927 | 約 $1.01 | $1.50 |
| dev(同上) | 927 | 約 $1.00 | $1.50 |
| 合計 | 1,899 | 約 $2.06 | $3.10 |

- 約9割は gpt-6-sol です(1回あたり最大 約 $0.0044)。
- 実行スクリプトは、各件を呼ぶ前に「その件の9構成をすべて最大の単価で呼んだ場合の費用」を足して上限を超えるかを見て、超えるならその件を呼ばずに止まります。
- 上限で止まった場合は、そこまでの結果で summary を書かず、報告します。

## 8. 決めておくこと

- **test の結果を見たあとで、説明文・指示文・正解・構成・指標を変えません。**
- 本番の実行は test・dev とも1回だけです。何回か回して良い回を選ぶことはしません。
- 実行スクリプトの不具合で結果が使えないとわかった場合は、直してそのセットを最初から全部やり直し、やり直したことと理由を summary に書きます。最初の生データも消さずに残します。
- 主な結論は test の数字で言います。dev の数字は参考として並べ、dev だけで言えることは結論にしません。

### summary の構成

1. **test の比較表(主)**: 9構成の、答えと一致した割合 [95%CI]、別解込み、判定時間 p50 / p95、1000回あたりの費用(実績 / 毎回キャッシュ切れ)、失敗の件数
2. **Jev と各 LLM の McNemar 検定(test)**: 12候補・6分類それぞれ。b、c、p、Holm 補正後の p
3. **dev の比較表(参考)**: 1 と同じ列
4. **わかったこと**: test の数字と検定から言えることだけ
5. **言えないこと**: 少なくとも次のことを書く
   - **test の発話は dev より長い**(平均 29.3文字 対 15.8文字)。LLM が作った発話は情報が多く、分類しやすい可能性がある
   - **test は、狙った分類と正解が、境目の25件も含めて100件すべて一致した。** 分類しやすい発話に寄っている可能性がある
   - データは合成で、正解は Claude Opus 5.5 が基準書から付けたラベルを人が確認したもの
   - 判定時間は1台の端末・1回の実行で測ったもの
   - 応答の品質(選んだプロンプトで答えたときの回答の良さ)は測っていない
   - 6分類はこの検証で作ったまとめ方で、本番の分類とは別物
   - 有意でない比較は「差がない」ことを示さない
6. **v2 から v3 で変わった点と、数字の動き**: 6 の表の変更点と、dev での v2 → v3 の正解率の変化。dev の数字の変化には、説明文・正解・順番・リトライのどれが効いたかを分けられないことも書く
7. **Jev の確信度と正解率**(test・dev)
8. **取り違えと6分類の対応表**(test)
9. **ラベルの食い違い**: dev は v2 から正解が変わった7件と理由(`label-review.md` から)、test は全100件の一覧へのリンク
10. **この計画(PLAN.md)の要点と、計画から変えた点**(なければ「なし」)
